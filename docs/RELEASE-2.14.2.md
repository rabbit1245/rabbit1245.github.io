# K볼 2.14.2 — 대용량 저장 읽기와 원본을 보존하는 복구

2.14.0의 35세·바이에른 뮌헨 소속 스이쿤 커리어에서 진행 중 읽기 오류가 발생했고, 재접속 뒤 저장 목록은 남지만 ‘저장 스냅샷을 읽을 수 없습니다’가 나왔다는 제보를 반영했습니다. 사용자의 Edge 저장소와 원본은 이 환경에서 접근할 수 없으므로 해당 선수의 실제 복구 완료나 정확한 손상 원인을 주장하지 않습니다.

## 확인된 결함

- 저장 용량 범위는 1GiB인데 불러오기는 압축을 풀고 `Blob.text()`로 커리어 전체를 하나의 문자열로 만들었습니다. V8의 단일 문자열 한계를 넘거나 임시 문자열 메모리가 부족하면, 유효한 저장도 읽지 못할 수 있습니다.
- 압축 해제·크기·JSON 오류를 모두 같은 문구로 바꿔 표시했습니다. 기존 메시지만으로 실제 바이트 손상과 읽기 제한을 구분할 수 없었습니다.
- 저장 관리/이전 저장 복원은 플레이 화면의 메뉴에만 있어, 아예 불러오지 못하면 복구 진입도 막혔습니다.

정상 저장에 허용되는 JSON 공백을 붙인 **572,586,592바이트** 검수 저장에서 2.14.0의 동일한 오류를 재현했습니다. 새 경로는 원래 검사와 전체 필드 일치를 통과했습니다. 공백으로 문자열 한계를 재현한 통제 사례이며 사용자의 실제 저장은 아닙니다. [재현 결과](validation/release-2.14.2/large-read.json).

또한 기존의 **429,189,740바이트·30시즌·43세 은퇴 커리어**를 원래 바이트에서 gzip으로 압축해 읽었습니다. 전체 스키마·이벤트·원래 canonical SHA-256을 확인했습니다. [실제 장기 저장 검수](validation/release-2.14.2/real-large-read.json).

## 변경 사항

`json-reader.ts`는 큰 JSON을 제한된 하위 값으로 나눠 네이티브 JSON 파서에 전달합니다. 384MiB 이상에서는 거대한 단일 문자열을 만들지 않습니다. 작은 무압축 저장은 기존 네이티브 경로를 유지하고, 압축 저장은 실제 확장 크기와 압축 스트림 완료를 검사합니다. 새 파서는 기존 압축/무압축 자동 저장과 큰 JSON 파일 가져오기에 공통 적용합니다. 데이터·경기·원장·해시 검사를 생략하지 않습니다. 잘못된 JSON·잘린 압축·거짓 크기는 계속 거절합니다.

오류 문구는 압축 해제·크기 검사·JSON 해석·저장소 읽기를 구분합니다. 구분된 단계 역시 특정 커리어의 원인을 단독 확정하는 진단은 아닙니다.

시작 화면에 **저장·복구**를 추가했습니다. 불러오기 실패 시에도 보관함을 열어 다음을 실행할 수 있습니다.

1. **원본 저장 보관**: 정상 해석이 안 되어도 현재 저장과 이전 백업의 원래 Blob 바이트·변경 원장·메타데이터를 `.kball-recovery`로 다운로드합니다. 일반 플레이 JSON과 다른 복구용 형식입니다. 원본 저장소를 수정하지 않습니다.
2. **이전 저장 복원**: 이전 백업을 검증한 뒤 **새 슬롯**에 복구합니다. 실패한 현재 저장과 원래 백업은 덮어쓰지 않습니다. 복구본은 목록에 표시됩니다. 정상 백업이 없으면 복구 성공으로 표시하지 않습니다.

새로운 IndexedDB 버전으로 올리거나 기존 슬롯을 일괄 이관하지 않습니다. 사용자 요청의 마무리 밸런스 패치인 2.14.1과 2.14.0의 변경분 저장/배경 체크포인트를 포함합니다. 경기·능력치·OVR·수상·기록을 추가 변경한 버전은 아닙니다.

## 검수

- 저장·백업·손상·충돌·변경 원장·큰 JSON 파서 관련 **54개 통과**. 마지막 파서/복구 통합 **4개 통과**. [54개](validation/release-2.14.2/storage.tap), [최종 4개](validation/release-2.14.2/final-reader.tap).
- 큰 중첩 객체·배열·유니코드·이스케이프·잘린 JSON·잘못된 문법·압축 손상·확장 크기를 검사했습니다. 원래 체크섬/검증 경로를 유지합니다.
- 최종 HTML의 실제 IndexedDB에 손상을 주입해 불러오기 실패 → 원본 다운로드 → 별도 슬롯 복구 → 재접속 → 정상 JSON 내보내기를 확인했습니다. 실패한 원본과 기존 백업의 바이트가 보존됐고, 모바일 시작 화면에 가로 넘침이 없습니다. [브라우저 검수](validation/release-2.14.2/browser-recovery.json). 테스트의 ‘스이쿤 복구 검수’는 생성한 통제 선수이며 실제 제보 선수의 데이터가 아닙니다.
- TypeScript·프로덕션 빌드·단독 HTML 빌드 통과. Linux Chromium localhost 검수이며, Windows Edge file:// 직접 실행과 실제 스이쿤 저장 복구는 아직 확인하지 못했습니다. 전체 경기 코어와 새 30시즌 재시뮬레이션은 이번에 재실행하지 않았습니다.

## 사용자 복구 절차

기존 Edge 프로필과 저장 데이터를 유지하세요. 브라우저 데이터를 지우지 마세요. 게임을 닫고 새 HTML을 기존 게임과 같은 파일 경로/이름으로 놓은 뒤 같은 Edge 프로필에서 열어야 기존 저장소에 접근하기 쉽습니다. 시작 화면의 저장·복구에서 먼저 원본을 보관하고 불러오기를 시도하세요. 실패하면 이전 저장 복원으로 별도 슬롯을 만듭니다. 두 읽기가 모두 실패하면 `.kball-recovery`를 보관해 원본 바이트와 오류 단계를 조사해야 합니다. 정상 백업이나 원본 확인 없이 복구 가능성을 보장하지 않습니다.

복구 아카이브는 `KBALL-RECOVERY-V1\n` UTF-8 헤더, 4바이트 little-endian 매니페스트 길이, JSON 매니페스트, 매니페스트의 parts 순서로 이어지는 원래 Blob들로 구성합니다. 각 참조는 index/bytes/type을 포함하고 기존 저장의 해시·압축 정보·변경 원장을 보존합니다. 데이터나 파일 안의 코드를 실행하는 형식이 아닙니다.
