# K볼 2.11.2 · 진행·이적·저장 대기 시간

## 원인과 수정 범위

14시즌이 쌓인 실제 커리어 JSON(272,717,105바이트)에서 파일 가져오기, 재실행, 훈련 선택/확정, 이적 창/수락, 다음 시즌, 실제 전·후반기와 JSON 내보내기를 각각 측정했다. 저장/경기 Worker의 요청·복사·응답 시간을 따로 기록했다. 큰 경기 계산 뒤 전체 저장을 만드는 단계가 대기 시간의 큰 부분이었다.

기존 JSON Blob 작성기는 작은 문자열을 계속 연결한 뒤 모든 문자열 조각을 마지막 Blob 생성 때까지 보관했다. 수백 MB 기록에서는 연결 문자열의 내부 노드가 대량으로 남아 메모리 정리 시간을 늘렸다. CPU 프로파일에서도 이 구간의 GC 부담이 확인됐다. 새 작성기는 256KiB 단위로 문자열을 즉시 UTF-8 바이트로 바꾸고, Blob에는 바이트 조각을 전달한다. 긴 문자열 토큰도 그대로 인코딩한다. JSON 필드·배열 순서와 수치를 바꾸지 않는다.

저장 JSON과 정규 체크섬 작성에서 반복되는 속성 이름의 JSON 인코딩 결과도 재사용한다. 캐시는 호출 안에서만 존재하며 최대 4,096개·각 이름 256자 이하다. 값이나 하위 객체는 캐시하지 않는다. 전체 필드를 계속 순회하고 원래 정렬과 SHA-256을 수행하며, 구버전의 undefined 배열 처리 바이트도 유지한다.

이적 제안 새로 확인(`refreshOffers`)은 이미 작은 변경 저장 대상으로 등록돼 있었지만 경기 Worker 분기 목록에서 빠져 있었다. 이 때문에 전체 커리어가 Worker로 왕복 복사되고 변경 인증 정보도 끊어져 전체 저장으로 넘어갔다. 두 목록을 공유하도록 연결해 기존 변경 원장 경로를 사용한다. 구버전 세계 이관처럼 전체 저장이 필요한 경우의 검증 경로는 유지한다.

경기 엔진·OVR·능력치·성장·팀 캐리·수상·경제·대회·기록 산식은 변경하지 않았다. 경기 파일의 변경은 버전 표기 한 줄뿐이다. 저장 검증·원본 체크섬·손상 거부·백업·충돌 감지와 큰 작업 뒤 Worker 사본 해제도 유지한다. 기록 삭제, 이벤트 축약, 계산 생략이나 저장 검사 면제는 없다.

## 측정과 검수

개선 전 2.11.1과 개선 후 단일 HTML에 같은 커리어를 가져와 같은 버튼 순서로 진행한다. 다른 성능 작업을 동시에 실행하지 않고 한 번씩 측정한 값이며, 모든 PC의 보장값으로 해석하지 않는다. 훈련 항목 선택은 화면 반영, 상태 변경은 자동 저장 완료까지를 잰다. 가져오기는 파일 전송·전체 검증·새 슬롯 저장을 포함한다. 경기 진행 시간에는 실제 경기 계산이 포함된다.

측정 환경은 Linux Chromium과 localhost로 전달한 독립 HTML이다. 관리형 브라우저 정책이 file:// 접근을 차단하므로 Windows Edge의 로컬 파일 실행을 직접 측정했다고 주장하지 않는다. HTML의 자산은 내부에 포함되고 외부 요청이 없는지 별도로 검사한다.

| 작업 | 2.11.1 | 2.11.2 |
|---|---:|---:|
| 첫 실행 | 2.84초 | 3.03초 |
| 273MB 가져오기·검증·자동 저장 | 36.62초 | 27.40초 |
| 저장 슬롯 불러오기 | 14.13초 | 11.32초 |
| 훈련 화면 열기 | 0.097초 | 0.095초 |
| 훈련 항목 선택 | 0.046초 | 0.048초 |
| 훈련 계획 확정·저장 | 0.140초 | 0.146초 |
| 현재 제안이 있는 이적 창 열기 | 0.095초 | 0.086초 |
| 이적/재계약 수락·저장 | 32.03초 | 23.27초 |
| 다음 시즌 시작·저장 | 25.66초 | 18.63초 |
| 실제 전반기·저장 | 43.30초 | 34.43초 |
| 실제 후반기·결산·저장 | 44.95초 | 30.60초 |
| 진행한 JSON 내보내기 | 25.19초 | 13.62초 |
| 진행한 저장 재실행 | 15.25초 | 12.68초 |

큰 진행 작업은 이 측정에서 약 20~32%, JSON 내보내기는 약 46% 단축됐다. 훈련 같은 기존 작은 변경은 이 자료에서 이미 0.05~0.15초 수준이었다. 첫 실행은 개선 대상으로 삼지 않았고 이 단일 대조에서는 조금 더 걸렸다. 모든 구간이 빨라졌다고 표현하지 않는다.

예를 들어 이적 수락의 경기 Worker 응답은 6.39→6.37초로 거의 같고, 저장 Worker 응답이 25.29→16.30초로 줄었다. 다음 시즌 경기 계산도 4.97→5.02초로 거의 같았다. 이는 실제 계산량을 줄여 얻은 결과와 구분된다. 이적 창 측정에는 이미 최신 제안이 있으므로 `refreshOffers` 수정의 효과로 이 숫자를 설명하지 않는다. 해당 경로는 별도 Worker 차단/변경 원장 회귀 검사로 확인했다.

신규 인코딩의 Unicode·긴 문자열·청크 경계·다수 키·구형 undefined 배열 바이트, 이적 제안의 경량 경로와 기존 저장·위변조 거부·백업·충돌·압축·Worker 해제 검사 **53개를 모두 통과**했다. TypeScript·프로덕션·독립 HTML/ZIP 빌드와 PC/모바일 실제 흐름 **11항목**도 통과했다. 경기 산식이 바뀌지 않아 30시즌 전체 재시뮬레이션을 반복하지 않았다.

최종 HTML에서 같은 실제 커리어를 가져와 훈련 확정·재계약·다음 시즌·실제 전/후반기를 진행한 뒤 **305,876,862바이트 JSON**을 내보내고 다시 불러왔다. 페이지 오류·자동 저장 오류·renderer 종료·외부 자산 요청은 없었고, 마지막 재실행 완료 후 상주 전용 Worker는 0개였다.

원본 14시즌의 클럽 경기·스탯·수상, 국가대표 과거 기록과 모든 능력치가 같았다. 개선 전/후에 새로 계산한 시즌의 개인 스탯·전체 경기 이벤트·리그 표도 바이트 해시가 같았다. 전체 저장 검증과 정규 SHA-256을 다시 통과했고, 큰 JSON의 바이트 해시는 native JSON.stringify 결과와도 일치했다.
