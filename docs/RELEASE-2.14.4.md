# K볼 2.14.4 — 록 카발란 이어하기와 장기 저장 속도

2.14.3은 대형 객체 복사를 피했지만, 진행마다 약 1GB의 전체 상태를 압축해 다른 Worker로 보내고 다시 풀었습니다. 불러오기 완료만 확인한 이전 검수는 이 반복 비용과 느린 PC의 로딩 문제를 충분히 해결하지 못했습니다.

## 변경

- 경기 이벤트 전체를 손실 없이 압축해 메모리에 보관합니다. 배열 길이와 기록은 그대로이며, 경기 상세·기록 검사·내보내기에서 필요한 이벤트를 읽습니다. 펼친 이벤트는 최근 8경기까지만 캐시합니다. 이벤트를 삭제하거나 집계를 원본 대신 저장하지 않습니다.
- 장기 커리어는 현재 상태에서 계산하고 새 경기와 변경된 상태만 인증해 저장합니다. 기존 원본·백업·변경 원장은 보존합니다. 큰 전체 상태를 다른 Worker로 반복 전송하지 않습니다.
- 새 진행 기록은 이벤트 Blob과 압축된 메타데이터를 저장합니다. 메타데이터를 압축하지 않은 중간 수정에서는 크기 제한으로 전체 저장을 재생성해 153초가 걸렸습니다. 최종본은 같은 네 진행 모두 기존 스냅샷을 재생성하지 않습니다.
- 원본을 완전히 검증한 뒤 별도의 검증된 빠른 읽기 캐시를 만듭니다. 다음 접속은 원본의 버전·해시와 캐시 전체 메타데이터·이벤트 Blob 해시를 확인합니다. 손상·불일치·공간 부족이면 원본 검사로 돌아가며, 캐시가 원본 저장이나 백업을 덮어쓰지 않습니다.
- 최초 변환 상태와 진행률·경과 시간을 시작 화면에 표시합니다. 최초 검사는 여전히 시간이 필요합니다.

## 실제 세이브 측정

Linux Chromium 154, 최종 단독 HTML localhost, 기본 브라우저 힙 설정입니다. 같은 원본(리비전 950, 35세, 2044년 17라운드)으로 측정했습니다.

| 항목 | 최종 측정 |
| --- | ---: |
| 최초 원본 검사·변환·캐시 생성 | 119.8초 |
| 후반기 진행 + 자동 저장 | 17.8초 |
| 36세 다음 시즌 시작 + 자동 저장 | 6.7초 |
| 전반기 진행 + 자동 저장 | 16.5초 |
| 후반기 진행 + 자동 저장 | 18.5초 |
| 창을 닫고 재접속 + 이어하기 | 12.0초 |

리비전 950→967→968→985→1002, 35→36세까지 연속 진행했고 매번 메타데이터와 저장 해시가 일치했습니다. 최종 재접속에서도 리비전 1002가 그대로 유지됐습니다. 네 번 모두 기준 스냅샷 리비전 840을 유지해 전체 재생성 경로가 실행되지 않았습니다. [측정 결과](validation/release-2.14.4/browser.json).

최초 검사 시간을 재접속 시간에 섞어 보고하지 않습니다. PC 성능·디스크·캐시 유무에 따라 달라지며, 캐시를 지우거나 사용할 수 없으면 원본 검사가 다시 필요합니다. Windows Edge 직접 파일 실행은 이 환경에서 검수하지 못했습니다.

## 원본 보존과 검수

기존 JSON/gzip 저장과 복구 원본을 계속 읽습니다. 새 변경 기록은 이전 버전이 읽지 못하는 v2 형식을 사용하므로, 업데이트 전 복구 원본을 보관하고 새 진행에는 이 버전을 사용하세요. 경기 규칙·성장·능력치·수상 계산은 변경하지 않습니다.

기존 저장·변경 원장·JSON 검사 37개와 추가 압축 배열·캐시 손상 거부·새 진행 기록 재생·해시/Worker 검사 10개가 통과했습니다. [기존 회귀](validation/release-2.14.4/legacy-regressions.tap), [추가 검사](validation/release-2.14.4/new-format.tap). 웹/단독 HTML 빌드와 TypeScript 검사도 통과했습니다. 실제 사용자 저장은 공개 저장소에 포함하지 않습니다.

진행 후 복구 파일을 전체 코어로 다시 검증했고, 원래 18시즌·602경기 및 대표팀 과거 기록 47개의 전체 필드 SHA-256이 일치했습니다. [원본 대조](validation/release-2.14.4/history-audit.json).
