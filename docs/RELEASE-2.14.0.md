# K볼 2.14.0 — 진행을 막던 전체 저장을 변경분 저장으로 전환

주장 승낙·이적·반시즌·시즌 전환의 계산과 기록을 보존하면서 매번 커리어 전체를 다시 검사·직렬화·압축하던 경로를 줄였습니다. 의미 있는 결정은 IndexedDB 트랜잭션이 끝난 뒤 다음 조작을 허용하므로, 자동 저장을 늦춰 저장 전 진행을 잃는 방식이 아닙니다.

## 실제 원인

2.13.0의 `App.command`는 게임 결과를 받은 뒤 `commit`의 저장이 끝나야 조작 잠금을 해제했습니다. 이적·주장 승낙은 경량 명령 목록에 없어 전체 상태를 Worker로 보냈고, 돌아온 결과를 다시 저장 Worker에 보내 전체 검증·canonical 체크섬·JSON 직렬화·gzip을 수행했습니다. 14시즌 파일에서는 계약 계산 응답보다 그 뒤의 전체 저장에 더 많은 시간이 들었습니다.

기존의 작은 변경 원장은 능력치 조정 등 일부 명령에만 적용됐습니다. 반시즌은 주차마다 리비전이 증가하므로 단일 결정의 `+1` 규칙을 그대로 적용할 수 없었습니다. 새 원장은 한 명령이 실제 진행한 범위 전체를 하나의 원자적 저장으로 다룹니다.

이미 저장된 상태에서 누른 ‘지금 저장’도 큰 검사와 압축을 끝낸 뒤에야 같은 내용임을 확인했습니다. 작은 원장 뒤에는 짧게는 1.5초 후 전체 체크포인트가 시작되어 조작 도중 작업을 반복하기도 했습니다.

## 실제로 확인한 다른 게임의 구조

- [ZenGM 공개 소스 · Cache.flush](https://github.com/zengm-games/zengm/blob/dcaf4620cbb09d2ebf599414d9850d60f90869b3/src/worker/db/Cache.ts#L846): 변경된 레코드·삭제 ID를 추적하고, 변경이 없으면 트랜잭션을 생략합니다. 변경된 store와 ID만 원자적으로 반영하고 실패하면 대기 집합을 되돌립니다. K볼에는 **변경분을 먼저 영구 반영하고 큰 재정리를 묶는 원리**를 적용했습니다. 코드를 복사하거나 시뮬레이션을 다른 게임의 규칙으로 바꾸지는 않았습니다.
- 사용자가 제공한 Astra v6의 `web/app.mjs`도 생성·성장·진행·은퇴·메뉴 이동에서 `await autosave()`를 호출합니다. 저장 횟수와 함께 저장 대상의 크기와 반복 처리를 살펴야 합니다. 실제 소스의 함수와 SHA-256은 [비교 근거](validation/release-2.14.0/references.json)에 남겼습니다. 다른 게임의 실행 속도를 직접 측정한 결과라고 주장하지 않습니다.

## 변경한 저장 흐름

| 동작 | 2.14.0 처리 |
|---|---|
| 화면 이동·훈련 초안·실제 변화가 없는 명령 | 저장하지 않음 |
| 이미 저장된 상태의 ‘지금 저장’ | 전체 작업 없이 저장 완료 안내 |
| 주장 응답·제안 넘기기 | 경기 Worker와 전체 월드 복사 없이 작은 변경 원장 반영 |
| 이적·잔류·직접 계약 해지 | 새 상태 검증 후 변경된 계약·클럽·선수 항목을 작은 원장으로 반영 |
| 반시즌·시즌 시작/종료·은퇴 | 기존 경기 계산 후 새/변경 데이터와 과거 불변 기록 참조를 저장 |
| 최초 저장·가져오기·JSON 내보내기·복원 | 필요한 전체 검증과 체크섬 유지 |
| 큰 전체 저장본 재정리 | 입력이 멈춘 시간에 묶어서 실행; 새 조작이 시작되면 연기 |

게임 Worker가 이미 만든 결과에서 과거 경기 원장을 다시 복사하지 않는 저장용 Blob을 함께 준비합니다. 큰 결과를 다시 저장 Worker에 보내 같은 전체 커리어를 재처리하지 않습니다. 원본 경기·이벤트·참여 선수·세부 스탯을 생략하지 않으며, 해시로 연결된 저장 원장이 바뀐 전체 데이터를 보존합니다.

초기 상태와 새 결과는 깊은 불변 상태로 보호합니다. 이미 검증된 **동일한 경기 객체**만 검증을 재사용하고, 새 경기·복사되어 바뀐 경기·변경된 값과 합계는 다시 검사합니다. 새 결과 검사는 저장 전에 끝납니다. 임의의 파일과 신뢰되지 않은 가변 객체는 기존의 전체 검사 경로를 사용합니다. 외부 JSON은 계속 전체 체크섬과 데이터 검사를 받습니다.

전체 체크포인트는 작은 저장에서 30초, 큰 저장에서 120초의 조용한 시간을 기다립니다. 변경분이 많이 쌓이면 15초의 조용한 시간 후 정리하며, 입력은 타이머를 연기합니다. 실행 중인 배경 체크포인트는 새 명령에 양보합니다. 원장 개수·용량의 안전 한도에서는 전체 저장으로 전환해 복원 비용을 제한합니다. 모든 상태를 무한히 쌓아 두는 구조는 아닙니다.

IndexedDB 내부는 기존 `kball-blob-v1`과 새 `kball-blob-v2`를 모두 읽습니다. 외부 JSON과 은퇴 TXT의 데이터 구조·원본 기록은 유지합니다. 자동 저장을 포함해 다중 탭 충돌·삭제된 슬롯 보호·직전 정상본 백업·체크포인트와 새 명령의 겹침 처리도 유지합니다. 6시즌 이상에서 큰 경기 Worker를 명령 사이에 해제하는 기존 메모리 정책도 유지합니다.

## 같은 파일의 전후 측정

Linux Chromium, localhost에서 동일한 단독 HTML을 실행했습니다. 동일한 14시즌 파일과 순서로 조작했고 아래는 단회 대조입니다. Windows Edge 파일 실행의 보장 시간이나 여러 기기의 평균이 아닙니다. [전 판](validation/release-2.14.0/progress-before.json), [개선 판](validation/release-2.14.0/progress-after.json), [주장 전](validation/release-2.14.0/captain-before.json), [주장 후](validation/release-2.14.0/captain-after.json).

| 동작 | 2.13.0 | 2.14.0 |
|---|---:|---:|
| 주장 수락 | 16.69초 | **0.17초** |
| 이미 저장된 상태의 ‘지금 저장’ | 15.62초 | **0.11초** |
| 계약 수락 | 16.62초 | **1.62초** |
| 다음 시즌 시작 | 17.68초 | **4.89초** |
| 전반기 진행 + 자동 저장 | 33.12초 | **19.36초** |
| 최초 JSON 가져오기 + 저장 | 23.71초 | 22.45초 |

주장 측정은 같은 14시즌 기록에 현재 능력치·리더십과 정상 제의를 준비한 통제 파일입니다. 경기·과거 기록을 새로 만들지 않았습니다. 두 판의 입력 파일과 해시는 [입력 근거](validation/release-2.14.0/fixtures.json)를 참조하세요.

반시즌 결과는 새 데이터 약 155MB를 저장 원장 Blob 약 10MB로 전달한 사례입니다. 이 작업 뒤 추가 전체 `prepare` 요청이 없음을 Worker 추적으로 확인했습니다. 이전 경기의 전체 저장을 반복하지 않아도 실제 경기 계산·새 결과 검사·데이터 기록 시간은 남습니다. 첫 가져오기와 불러오기는 전체 자료를 인증해야 하므로 작은 결정처럼 즉시 끝나지 않습니다.

- 전체 코어 **440개 통과, 실패 0, 기존 30시즌 재시뮬레이션 1개 제외**. [결과](validation/release-2.14.0/core.tap). 제외한 장기 검사의 기존 테스트 체크포인트 문자열 한계는 2.13.0 보고서와 같습니다.
- 저장·복구·체크포인트·Worker 회귀 **21개 통과**. [결과](validation/release-2.14.0/storage.tap).
- 변경 원장·다중 라운드 리비전·실제 계약·FA·충돌·손상·은퇴 보존 **8개 통과**. [결과](validation/release-2.14.0/delta.tap).
- 마지막 클라이언트·스케줄러·변경 원장 통합 **11개 통과**, 최종 단독 HTML의 기존 저장 가져오기·이관·원본 기록·재접속 검사도 통과했습니다. [통합 검사](validation/release-2.14.0/final-targeted.tap), [최종 HTML](validation/release-2.14.0/final-import-ui.json).
- 고정 시드와 같은 명령으로 6라운드를 진행한 **전체 커리어 데이터** canonical SHA-256이 전후 동일합니다. 사용자 6경기, 월드 3,515경기 처리 상태와 모든 이벤트·참여 선수·기록을 포함합니다. [전체 데이터 대조](validation/release-2.14.0/simulation.json).
- 실제 14시즌 저장으로 이적·다음 시즌·전반기 이후 재접속하고 **4,696개 경기의 식별자·스코어·개인 스탯·이벤트 수, 전체 시즌 집계·능력치**가 일치함을 확인했습니다. [재접속](validation/release-2.14.0/durability.json).
- 후반기·시즌 종료도 진행한 뒤 다시 불러와 같은 기록 검사를 통과했습니다. 별도 실행에서 후반기+시즌 종료는 약 15.4초였으며, 이 수치는 전 판과의 대조값이 아닙니다. [전체 시즌](validation/release-2.14.0/complete-season.json), [종료 후 재접속](validation/release-2.14.0/season-end.json).
- 주장 수락 후 재접속에서도 역할·최신 리비전·검사 정보가 유지됐습니다. 이미 저장된 상태의 재저장은 Worker나 전체 저장본 갱신을 만들지 않았습니다.

게임의 능력치·OVR·성장·전술·결과 산식·수상·이적 조건을 바꾼 패치가 아닙니다. 핵심 수정 위치는 `game-delta.ts`, `save-codec.ts`, `storage.ts`, `worker.ts`, `client.ts`, `command-patches.ts`, `checkpoint-scheduler.ts`, `App.tsx`입니다.
